Behavioral Design Pattern

One change.
Many reactions.

The Observer pattern lets an object broadcast that its state changed, without ever needing to know who's listening, or what they'll do about it.

01 — Intent

Define a one-to-many dependency between objects.

Observer is a behavioral design pattern that lets you define a subscription mechanism so that multiple objects — observers — are notified automatically whenever the object they're watching — the subject — changes state.

The subject never hard-codes who it's talking to. It just keeps a list of subscribers and calls them all when something worth knowing about happens.

02 — Motivation

What goes wrong without it

Picture a weather station. The temperature updates, and five different parts of the app need to know: a display, a graph, a stats panel, a mobile alert, a push notification. The obvious first pass is to have the weather station call each one directly.

✕ Direct calls

Every new component means editing WeatherStation again. It knows too much about its dependents — tight coupling.

✓ Through an Observer interface

The station only knows about the Observer interface. New listeners attach themselves — no edits upstream.

03 — The everyday version

Think: YouTube subscriptions

A channel doesn't ping every viewer individually to ask if they want to know about a new upload. People subscribe once. When a video drops, the channel notifies its subscriber list — and it works exactly the same whether there are ten subscribers or ten million.

Channel → Subject. Subscribers → Observers. New upload → the change that triggers notification.

04 — Structure

Four moving parts

SubjectHolds the state and the list of observers. Exposes attach / detach / notify.
ObserverA common interface every listener implements — usually just update().
ConcreteSubjectThe real object whose state actually changes (e.g. WeatherStation).
ConcreteObserverThe real listener (e.g. TemperatureDisplay) — decides how to react.

05 — Workflow

Subscribe → Change → Notify → Update

Each registered observer receives the update in turn — one state change can ripple out to any number of listeners without the subject ever branching on "if this observer, then that."

06 — Pseudocode

The shape of it, language-agnostic

interface Observer:
    update(data)

interface Subject:
    attach(observer)
    detach(observer)
    notify()

class ConcreteSubject implements Subject:
    observers = []
    state = null

    attach(observer):
        observers.add(observer)

    detach(observer):
        observers.remove(observer)

    notify():
        for observer in observers:
            observer.update(state)

    setState(newState):
        state = newState
        notify()

class ConcreteObserver implements Observer:
    update(data):
        // react to the new data, however this observer needs to

07 — Worked example

A weather station, end to end

The classic teaching example: one subject, two very different observers, zero coupling between them.

class Observer:
    def update(self, temperature): pass

class WeatherStation:
    def __init__(self):
        self.observers = []
        self.temperature = 0

    def attach(self, observer):
        self.observers.append(observer)

    def detach(self, observer):
        self.observers.remove(observer)

    def notify(self):
        for observer in self.observers:
            observer.update(self.temperature)

    def set_temperature(self, temperature):
        self.temperature = temperature
        self.notify()

class TemperatureDisplay(Observer):
    def update(self, temperature):
        print(f"Display: {temperature}°C")

class WeatherAlert(Observer):
    def update(self, temperature):
        if temperature > 40:
            print("Alert: very high temperature!")

station = WeatherStation()
station.attach(TemperatureDisplay())
station.attach(WeatherAlert())

station.set_temperature(35)   # Display: 35°C
station.set_temperature(42)   # Display: 42°C  /  Alert: very high temperature!

Adding a MobileApp observer later means writing one new class and calling attach() — WeatherStation is never touched again. That's the Open/Closed Principle in action.

08 — Two delivery styles

Push vs. pull

Push

The subject sends the changed data straight to update(data). Simple, but couples the signature to exactly what the subject has on hand.

Pull

The subject just says "something changed." Each observer calls back into the subject for whatever fields it actually needs. More flexible, one extra round trip.

09 — Applicability

Reach for it when…

  • One object's change should trigger updates in an unknown or changing number of other objects.
  • You want subject and observers to stay loosely coupled and independently testable.
  • Observers need to subscribe and unsubscribe dynamically, at runtime.
  • You're building anything event-driven: GUIs, notification systems, live dashboards, monitoring.

Think twice when…

  • There are only two objects and a direct call is simpler to trace.
  • Notification order matters a lot and is hard to guarantee.
  • You'd end up with thousands of observers — notification cost adds up.

10 — Trade-offs

Pros and cons

+ Advantages
  • Loose coupling — the subject depends on an interface, not concrete classes.
  • New observers plug in without touching the subject (Open/Closed Principle).
  • Subscriptions are dynamic — attach and detach at runtime.
  • Clean separation: subject manages state, observers decide how to react.
− Disadvantages
  • Observers are notified in unspecified order by default — don't rely on it.
  • Chains of updates triggering further updates can get hard to trace.
  • Forgetting to detach() leaks memory — observers outlive their usefulness.
  • A very large observer list makes every state change proportionally expensive.

11 — Where it shows up

You've already used this pattern

DOM event listeners

button.addEventListener('click', …) — one click, any number of handlers.

Stock tickers

A price feed pushes updates to trading apps, dashboards, and alerts simultaneously.

Order tracking

Status changes fan out to the customer app, email, SMS, and the delivery dashboard.

Chat apps

One new message updates the chat window, the badge count, and the notification sound.

Reactive UI state

Modern frameworks re-render components when the state they subscribe to changes.

"Back in stock" alerts

Shoppers subscribe to a product; restocking notifies everyone who asked.

12 — Nearby patterns

Don't confuse it with…

Publish–Subscribe: a close cousin. Classic Observer has the subject hold the observer list directly; Pub/Sub usually routes through a broker or event bus, so publishers and subscribers never see each other at all.

Polling: the opposite instinct — repeatedly asking "did it change yet?" instead of being told. Observer trades a wasteful loop for an on-demand callback.

Strategy: also behavioral, but solves a different problem — picking one interchangeable algorithm, not broadcasting a change to many listeners.
